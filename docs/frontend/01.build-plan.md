# Build Plan

This plan covers the shared theme foundation and approximately 80–90% of the intended storefront experience before implementation. The theme remains a presentation layer: WordPress and WooCommerce own content, store behavior, and persistent data.

Use the [UI Registry](09.ui-registry.md) for component requirements and the [Project Tracker](../07.project-tracker.md) for progress. Do not begin a UI element until its registry entry is `SPECIFIED` and has no unresolved decisions that affect its implementation.

## Phase 0 — Pre-development foundation

Global tokens are approved, and the shared header and footer are specified. Phase 1 may begin.

**Phase 1 gate:** global tokens are approved and all Phase 1 UI Registry entries are `SPECIFIED`.

**Phase 2 gate:** before Phase 2 starts, all Phase 2 UI Registry entries must be `SPECIFIED`, with no unresolved decisions delegated to the implementer. Homepage imagery must have an approved crop, adequate resolution, and documented source/license/use terms before it is shipped.

## Phase 1 — Theme foundation and shared shell

### Deliverables

- Initialize and activate the Alice Block Theme.
- Establish approved presets and global styles in `theme.json` and CSS.
- Build the approved fixed-composition header: fixed on mobile, with the sliding navigation panel; on desktop it hides on downward scroll and returns on upward scroll. Preserve native search/account/cart destinations.
- Build a native footer using approved editable site content and navigation. Do not add signup, cookie-management, or service functionality.
- Keep general WordPress pages usable when WooCommerce is inactive; show the agreed administrator notice without fatal errors.

### Acceptance

- Layout composition stays fixed while intended logo, navigation items, and editable content remain available to the merchant.
- WooCommerce deactivation does not fatal; store-specific output can be absent and general content still renders.
- Header/footer meet the responsive and accessibility criteria in the UI Registry.

## Phase 2 — Core shopping experience

### Deliverables

Implement the native-block homepage, product catalog/category/tag archives, product detail, product search/results, My Account, Cart, and Checkout presentation.

- Homepage: ship the specified editorial copy and licensed, locally bundled desktop/mobile hero images; include a native WooCommerce product collection. Activation must not create pages, products, or other database records.
- Catalog/search: use native WooCommerce product collection/query and search controls. Present native sorting/filtering only where the supported blocks provide it; do not create custom filtering behavior.
- Product detail: present WooCommerce-provided imagery, title, price/sale, availability, description, variation and quantity controls, and add-to-cart behavior.
- Cart and Checkout: support WooCommerce block-based pages and classic shortcode-backed pages. Prefer blocks in new/default setups and preserve each mode’s validation and commerce behavior.
- Account: style the native My Account page and endpoints without adding account behavior.

### Acceptance

- The product collection remains composed and understandable with no products.
- Product data and native controls present correctly for simple and variable products, sale pricing, and unavailable/out-of-stock products.
- Empty/populated carts, checkout errors and confirmation states, account endpoints, search results, and empty search results remain usable.
- No theme code owns pricing, variation resolution, filtering, cart state, checkout, payment, shipping, or order logic.

## Phase 3 — Editorial and secondary templates

### Inventory

Implement the blog/posts index, category/archive, single post, standard pages, product archive fallback, search fallback, and 404 presentation listed in the [Sitemap](../architecture/02-sitemap.md).

### Gate

Before each item starts, complete its Registry entry for content hierarchy, editable areas, locking, responsive behavior, and accessibility. Details may be decided at this phase; no implementation decision is delegated to the agent.

## Phase 4 — Compatibility and quality review

- Run relevant existing lint, build, and validation checks. Do not create a new test suite without approval.
- Manually review the supported browser range at mobile, tablet, and desktop widths; include editor/template-locking behavior and the scenarios below.
- Apply the accessibility and performance acceptance criteria in the [Design System](04-design-system.md) and [Technical Architecture](../architecture/05.technical-architecture.md). Record reference-store conditions with performance results.
- Provide the project owner with manual review steps and any unverified cases.

### Manual review matrix

- No WooCommerce; general WordPress content still renders and the administrator notice appears.
- Empty and populated catalogs; simple, variable, sale, and unavailable products; product search with results and no results.
- Empty/populated cart and quantity/removal feedback in both Cart modes; checkout validation, processing/failure, and confirmation in both Checkout modes using a non-production gateway.
- Logged-out account and representative account endpoints.
- Header/footer and merchant content editing/locking across desktop, tablet, and mobile.

## Out of plan

Anything requiring custom blocks, custom business behavior, new persistent data, or a new plugin/service must stop for project-owner review under the [Custom Block Consideration List](../consideration-list.md).
