# Build Plan

This plan covers the shared theme foundation and approximately 80–90% of the intended storefront experience before implementation. The theme remains a presentation layer: WordPress and WooCommerce own content, store behavior, and persistent data.

Use the [UI Registry](09.ui-registry.md) for component requirements and the [Project Tracker](../07.project-tracker.md) for progress. Do not begin a UI element until its registry entry is `SPECIFIED` and has no unresolved decisions that affect its implementation.

## Phase 0 — Pre-development foundation

Global tokens are approved, and the shared header and footer are specified. Phase 1 may begin.

**Phase 1 gate:** global tokens are approved and all Phase 1 UI Registry entries are `SPECIFIED`.

**Phase 2 gate:** before implementation, the Homepage Hero UI Registry entry must be `SPECIFIED`. Record source/license/use terms for supplied example images before public distribution.

## Phase 1 — Theme foundation and shared shell

**Progress:** Implementation complete and ready for WordPress admin review. Record activation, responsive/editor review, general-content fallback, and WooCommerce-inactive notice verification in the Project Tracker. Phase 2 remains gated by its UI Registry specifications.

### Deliverables

- Initialize the Alice Block Theme scaffold and make it available for activation.
- Establish approved presets and global styles in `theme.json` and CSS.
- Provide the required fallback template and basic native page/single content rendering so WordPress pages work during setup.
- Build the approved fixed-composition header with a sliding navigation panel; it hides on downward scroll and returns on upward scroll at all widths. Preserve native search/account/cart destinations.
- Build a native footer using approved editable site content and navigation. Do not add signup, cookie-management, or service functionality.
- Keep general WordPress pages usable when WooCommerce is inactive; show the agreed administrator notice without fatal errors.

### Acceptance

- Layout composition stays fixed while intended logo, navigation items, and editable content remain available to the merchant.
- WooCommerce deactivation does not fatal; store-specific output can be absent and general content still renders.
- Header/footer meet the responsive and accessibility criteria in the UI Registry.

## Phase 2 — Homepage hero

### Deliverables

- Build the fixed homepage hero from a native Gallery block, a shared editable text/button overlay, and a removable native tint Group. Merchants can add, replace, or remove hero images and choose a preset text position; the hero frame stays fixed.
- Progressively enhance a Gallery with two or more images into a pinned, scroll-driven sequence through the Interactivity API. Each image remains visible for about one viewport of downward or upward scrolling, the next/previous image changes near the end of that interval, and normal page scrolling resumes after the final image has had its interval.
- Show a static first-slide preview with overlay/tint in the Site Editor; the live site gets the scroll interaction. Use a centered responsive crop and document the central safe-area image assumption; do not add a separate mobile crop step.
- Provide a no-JavaScript presentation that keeps all images and content available. Honor reduced-motion preferences and avoid controls that are not needed for the scroll interaction.
- Do not seed pages or other database content. The product collection and remaining catalog, product, search, account, Cart, and Checkout work stay deferred until a later phase is scheduled.

### Acceptance

- Merchants can edit hero copy and button, replace/add images, select a preset text position, and remove the optional tint without removing the hero frame.
- Scrolling advances or reverses one slide near the end of each viewport interval. The final slide remains pinned for its interval before the hero releases and normal page scrolling continues. A Gallery with one image remains a static hero without a pinned scroll sequence.
- The editor shows the first-slide composition; a centered safe area preserves key photo elements through mobile cropping at mobile, tablet, and desktop widths. Text/link remain keyboard accessible and reduced-motion is honored.
- Theme code only changes visual presentation; WordPress owns the image and text content.

## Phase 3 — Editorial and secondary templates

### Inventory

Implement the blog/posts index, category/archive, single post, standard pages, product archive fallback, search fallback, and 404 presentation listed in the [Sitemap](../architecture/02-sitemap.md).

### Gate

Before adding richer layouts for each item, complete its Registry entry for content hierarchy, editable areas, locking, responsive behavior, and accessibility. Phase 1's basic page/single renderers remain the functional fallback until those refinements are specified.

## Phase 4 — Compatibility and quality review

- Run relevant existing lint, build, and validation checks. Do not create a new test suite without approval.
- Manually review the supported browser range at mobile, tablet, and desktop widths; include editor/template-locking behavior and the scenarios below.
- Apply the accessibility and performance acceptance criteria in [Design Foundations](design-system-reference.html) and [Technical Architecture](../architecture/05.technical-architecture.md). Record reference-store conditions with performance results.
- Provide the project owner with manual review steps and any unverified cases.

### Manual review matrix

- No WooCommerce; general WordPress content still renders and the administrator notice appears.
- Empty and populated catalogs; simple, variable, sale, and unavailable products; product search with results and no results.
- Empty/populated cart and quantity/removal feedback in both Cart modes; checkout validation, processing/failure, and confirmation in both Checkout modes using a non-production gateway.
- Logged-out account and representative account endpoints.
- Header/footer and merchant content editing/locking across desktop, tablet, and mobile.

## Out of plan

Anything requiring custom blocks, custom business behavior, new persistent data, or a new plugin/service must stop for project-owner review under the [Custom Block Consideration List](../consideration-list.md).
