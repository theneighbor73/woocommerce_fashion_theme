# Technical Architecture

## Responsibility boundary

The theme is a presentation layer. WordPress and WooCommerce remain responsible for data, editing, navigation, product behavior, cart, checkout, payment, shipping, accounts, and orders. The theme must not add custom business data or replace native behavior.

Use native block templates, template parts, patterns, `theme.json`, and CSS. JavaScript is limited to progressive visual/interface interactions; use the Interactivity API only where native blocks and CSS do not provide the needed visual state, including scroll-driven hero slides. Do not use it to implement shopping features. See [the project overview](../00.project-overview.md) for the scope boundary and escalation process.

## Block theme structure

Use WordPress's normal block theme locations:

- `style.css` — theme metadata.
- `theme.json` — global settings, approved presets, and default block styles.
- `templates/*.html` — page templates following the WordPress template hierarchy.
- `parts/*.html` — reusable structural regions such as header and footer.
- `patterns/*.php` — reusable compositions of native blocks where useful.
- `assets/css/` and `assets/js/` — presentation and approved progressive enhancements.
- `functions.php` and focused `inc/*.php` modules — theme setup, asset loading, and guarded WooCommerce presentation integration only.

Do not create files or directories speculatively. Do not put PHP in block HTML templates or template parts.

## Reusable merchant components

- Build insertable page sections from native blocks and register them as block patterns in `patterns/`.
- Use the registered pattern as the source composition in templates when the same section appears there, rather than maintaining duplicate block markup.
- Pattern insertions are independent editable copies. Use template parts for shared site structure that should be maintained in one place, such as the header and footer.
- Prefer this pattern-and-template-part approach over custom blocks for portable visual components; custom blocks remain outside the theme boundary.

## WooCommerce integration

- Prefer WooCommerce blocks and documented integration APIs.
- Support both WooCommerce block-based and classic shortcode-backed Cart and Checkout pages. Prefer native blocks for new/default setups; preserve the presentation of classic pages without replacing their behavior.
- Use other WooCommerce template mechanisms only where required by the approved UI specification.
- Avoid copying plugin templates or reproducing validation, pricing, cart, checkout, payment, inventory, or account logic.
- Guard WooCommerce-specific calls so the theme remains usable for general WordPress content while WooCommerce is inactive. Store UI may be absent in that state.
- Check APIs against the minimum WordPress, WooCommerce, and PHP versions in the project overview. Verify responsive presentation in the documented browser support range.

## Assets and accessibility

Use the CSS skill for stylesheet organization, design tokens, cascade, and responsive rules. Use the JS skill before adding script behavior. Use the PHP/HTML skill for escaping, theme hooks, patterns, and block markup. Keep assets lightweight and conditionally loaded where practical.

Use semantic native controls, keyboard-accessible interactions, visible focus, appropriate accessible names, and reduced-motion support. Follow contrast values in the design system and approved palette.

## Performance acceptance

Target “good” Core Web Vitals on the controlled reference store at the 75th percentile: LCP ≤ 2.5 seconds, INP ≤ 200 ms, and CLS ≤ 0.1 ([Google guidance](https://developers.google.com/search/docs/appearance/core-web-vitals)). Record the host, catalog/media fixture, browser, and active plugins with results because page-level performance is not controlled by the theme alone. When field data is unavailable, use lab measurements to track regressions and label them provisional rather than claiming a field pass.

## Verification expectations

Review theme-authored UI against WCAG 2.2 Level AA ([W3C standard](https://www.w3.org/TR/WCAG22/)); treat core/plugin UI as a compatibility surface and verify theme styling has not degraded it. For validation commands, tool permissions, and review procedures, follow [the Agent Toolkit](../../toolkit.md).

## Development tools and access

The [Agent Toolkit](../../toolkit.md) is the single source for approved development tools, WP-CLI invocation, filesystem and debug-log access, credentials, verification ownership, and required approvals.

The verified local CLI stack is WordPress 7.1.4, WooCommerce 10.8.1, WP-CLI 2.12.0, PHP 8.3.30, and MariaDB 11.4.9. These are local development versions, not replacements for the minimum supported versions in the Project Overview.

## Source of truth

Theme structure is maintained in the repository. The Site Editor may be used to inspect behavior, but manually created structural changes are not the source of truth. Document new UI work in `docs/frontend/09.ui-registry.md` and update progress in `docs/07.project-tracker.md` when implementation status changes.
