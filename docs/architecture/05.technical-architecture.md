# Technical Architecture

## Responsibility boundary

The theme is a presentation layer. WordPress and WooCommerce remain responsible for data, editing, navigation, product behavior, cart, checkout, payment, shipping, accounts, and orders. The theme must not add custom business data or replace native behavior.

Use native block templates, template parts, patterns, `theme.json`, and CSS. JavaScript is limited to progressive visual/interface interactions; use the Interactivity API only where native blocks and CSS do not provide the needed visual state. Do not use it to implement shopping features. See [the project overview](../00.project-overview.md) for the scope boundary and escalation process.

## Block theme structure

Use WordPress's normal block theme locations:

- `style.css` — theme metadata.
- `theme.json` — global settings, approved presets, and default block styles.
- `templates/*.html` — page templates following the WordPress template hierarchy.
- `parts/*.html` — reusable structural regions such as header and footer.
- `patterns/*.php` — reusable compositions of native blocks where useful.
- `assets/css/` and `assets/js/` — presentation and approved progressive enhancements.
- `functions.php` and focused `inc/*.php` modules — theme setup, asset loading, and guarded WooCommerce presentation integration only.

Do not create files or directories speculatively. Do not put PHP in block HTML templates or template parts.

## WooCommerce integration

- Prefer WooCommerce blocks and documented integration APIs.
- Use WooCommerce template mechanisms only where required by the approved UI specification.
- Avoid copying plugin templates or reproducing validation, pricing, cart, checkout, payment, inventory, or account logic.
- Guard WooCommerce-specific calls so the theme remains usable for general WordPress content while WooCommerce is inactive. Store UI may be absent in that state.
- Check relevant APIs against the local environment versions in the project overview; those versions are not a published minimum-support promise.

## Assets and accessibility

Use the CSS skill for stylesheet organization, design tokens, cascade, and responsive rules. Use the JS skill before adding script behavior. Use the PHP/HTML skill for escaping, theme hooks, patterns, and block markup. Keep assets lightweight and conditionally loaded where practical.

Use semantic native controls, keyboard-accessible interactions, visible focus, appropriate accessible names, and reduced-motion support. Follow contrast values in the design system and approved palette.

## Source of truth

Theme structure is maintained in the repository. The Site Editor may be used to inspect behavior, but manually created structural changes are not the source of truth. Document new UI work in `docs/frontend/09.ui-registry.md` and update progress in `docs/07.project-tracker.md` when implementation status changes.
