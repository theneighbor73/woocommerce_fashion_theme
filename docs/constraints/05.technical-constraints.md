# Technical Constraints

This document is the source of truth for project-wide implementation boundaries and technical quality requirements.

## Theme responsibility and allowed implementation

The theme is a presentation layer. WordPress and WooCommerce remain responsible for content, navigation, product data, variations, search, cart, checkout, accounts, payments, shipping, and orders. Use native WordPress and WooCommerce behavior; do not recreate business behavior or add custom business data.

Use native block templates, template parts, patterns, `theme.json`, and CSS for presentation. Use the Interactivity API only for narrowly scoped progressive visual/interface behavior that native blocks and CSS cannot provide, such as navigation state or scroll-driven hero slides. JavaScript must not replace or extend shopping behavior.

If a requirement cannot be met within this boundary, stop and present the native fallback and any existing-plugin option. The project owner decides whether to use a fallback, defer the work, or record the requirement in the [Custom Block Consideration List](../consideration-list.md). Do not implement a custom block or install a plugin without that decision.

## Theme structure

Use WordPress's normal block theme locations:

- `style.css` — theme metadata.
- `theme.json` — global settings, approved presets, and default block styles.
- `templates/*.html` — page templates following the WordPress template hierarchy.
- `parts/*.html` — recurring structural regions such as header and footer.
- `patterns/*.php` — reusable compositions of native blocks where useful.
- `assets/css/` and `assets/js/` — presentation and approved progressive enhancements.
- `functions.php` and focused `inc/*.php` modules — theme setup, asset loading, and guarded WooCommerce presentation integration only.

Do not create files or directories speculatively. Do not put PHP in block HTML templates or template parts.
Theme structure is maintained in the repository; the Site Editor may be used to inspect behavior, but manually created structural changes are not the source of truth.

## Reusable compositions and shared structure

- Build reusable merchant-facing page sections from native blocks and register them as inserter patterns. Pattern insertions are independent editable copies.
- Reuse the registered pattern as the source composition in templates where the same section appears; do not maintain duplicate block markup or create custom blocks just to package a component.
- Use template parts for recurring site structure that should be maintained in one place, such as the shared header and footer.
- Use the simplest appropriate CSS or progressive enhancement for visual components; a reusable visual element does not automatically need to be a WordPress block.

## Template composition and merchant editing

### Composition and locking

Templates and patterns have fixed compositions while intended content remains editable through native WordPress tools. Do not expose arbitrary template composition controls in the initial version. Use `contentOnly` locking where it supports this model; document the specific editing and locking behavior in the relevant UI Registry entry, including any justified exception.

### Style presets and merchant customization

- Register theme-defined block style variations as curated presets that encourage merchants to use the theme's design system consistently. Their purpose is to offer clear, ready-to-use choices, not to enforce a locked styling system.
- Keep native WordPress block styling and Site Editor customization available to merchants. Do not disable native styling controls solely to force preset use; merchants may adjust block settings or site-wide styles when needed.
- Choose Site Editor settings deliberately: configure supported controls individually in `theme.json`, including per-block settings where useful, instead of enabling the broad `appearanceTools` catch-all. Review newly available WordPress controls before exposing them to merchants.
- Expose only the approved color presets documented in UI Tokens. Do not add or change a color or merchant-facing color preset without the project owner's approval. Document each approved addition or change in both UI Tokens and Design Foundations, including its semantic role and verified foreground/background contrast pairings. Keep the token structure extensible for a possible future dark-mode switch, but do not predefine dark-mode colors or behavior before that work is approved.
- For custom block style variations that should be customizable in Global Styles, provide their style properties through the supported variation style data (`style_data`). WordPress can then expose those properties for editing and reset in the Site Editor. CSS-only rules such as `.is-style-primary` can style a variation on the frontend, but WordPress cannot expose those CSS declarations as editable variation settings in Global Styles.
- Preserve WordPress's native reset behavior: merchants can reset a variation's styles through its block and style-section reset controls. Individual block customizations are separate and use their own reset controls.
- Site Editor customizations are merchant-owned and take precedence over theme defaults. Theme updates must not overwrite saved user styles or use CSS to defeat them. Keep registered style-variation names stable; review any removal or rename for its effect on saved customizations. When reviewing a style change, check both theme defaults and a site with saved customizations, and confirm native reset returns to the current theme default.
- Specify the available presets and their intended visual roles in the UI Registry. Their default appearance must follow [Design Foundations](../frontend/design-system-reference.html) and [UI Tokens](../frontend/08.ui-tokens.md).

## Localization

- Make theme-authored user-facing strings and editor labels translation-ready using WordPress-supported translation mechanisms.
- Support translated content and interface strings in left-to-right languages. Check that longer translations remain readable and that controls, navigation, and templates still fit at supported viewport sizes.
- Right-to-left language support is out of scope; do not add RTL-specific layout or icon-mirroring work unless the project owner changes this decision.

## WooCommerce integration

- WooCommerce is required for the intended ecommerce storefront. If inactive, avoid fatal errors, continue to render general WordPress content, and give administrators an appropriate notice that WooCommerce is needed for store features.
- Prefer WooCommerce blocks and documented integration APIs. Use other WooCommerce template mechanisms only where required by the approved UI specification.
- Support both WooCommerce block-based and classic shortcode-backed Cart and Checkout pages. Prefer blocks for new/default setups; preserve both modes' behavior.
- Use the correct WordPress and WooCommerce template hierarchy. A WooCommerce page does not necessarily require a separate theme HTML template.
- Avoid copying plugin templates or reproducing validation, pricing, cart, checkout, payment, inventory, or account logic.
- Guard WooCommerce-specific calls so the theme remains usable for general WordPress content while WooCommerce is inactive. Store UI may be absent in that state.

## Compatibility baseline

For initial implementation and compatibility checks, these local environment versions are also the minimum platform versions:

| Component   | Minimum version |
| ----------- | --------------: |
| WordPress   |           7.1.4 |
| WooCommerce |          10.8.1 |
| PHP         |          8.3.30 |

Support the current and previous major versions of Chrome, Edge, Firefox, and Safari, including iOS Safari. Avoid relying on features unavailable in that browser range without a graceful fallback.

## Accessibility and performance quality

- Review theme-authored UI against WCAG 2.2 Level AA. Treat core/plugin UI as a compatibility surface and verify theme styling has not degraded it.
- Use semantic native controls, keyboard-accessible interactions, visible and unobscured focus, appropriate accessible names, and reduced-motion support. Follow contrast and palette requirements in the Design Foundations and UI Tokens.
- Target “good” Core Web Vitals on the controlled reference store at the 75th percentile: LCP ≤ 2.5 seconds, INP ≤ 200 ms, and CLS ≤ 0.1 ([Google guidance](https://developers.google.com/search/docs/appearance/core-web-vitals)). Record the host, catalog/media fixture, browser, and active plugins with results because page-level performance is not controlled by the theme alone. When field data is unavailable, use lab measurements to track regressions and label them provisional rather than claiming a field pass.
